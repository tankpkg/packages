# GCP to Pulumi Field Guide 2026

Sources: Pulumi CLI v3.252-v3.254 releases and import incident #14836, Pulumi GCP/Google Native/Terraform Bridge repositories, Terraform Google provider and Magic Modules releases/issues, Google Cloud Asset Inventory, IAM propagation, Bucket Lock, Cloud KMS, Cloud SQL, Shared VPC, and project lien documentation

Covers: provider viability, version floors, upstream inheritance, incomplete inventory, consistency windows, IAM/service-agent ownership, irreversible controls, stateful services, and cutover evidence.

## Provider Choice Is No Longer Symmetric

Use `@pulumi/gcp` / GCP Classic for new GCP adoption. As of 2026, the Google
Native repository says it is unmaintained and that no further releases or fixes
are planned. It directs all users to GCP Classic.

For existing Google Native resources:

1. Do not add new resources to the provider.
2. Record resource type, physical ID, parent, dependencies, and live fields.
3. Find the corresponding GCP Classic resource and import format.
4. Rehearse a remove-without-delete plus import in a copied stack/project.
5. Treat type aliases as identity aids only; they do not translate provider
   state or prove CRUD equivalence.

## Understand the Two Generation Layers

GCP Classic bridges the Terraform Google provider through
`pulumi-terraform-bridge`. The upstream Google provider is itself largely
generated by Magic Modules, with handwritten/custom code for exceptions.

The effective path is:

```text
Google API -> Magic Modules/custom provider code -> Terraform Google provider
           -> Pulumi Terraform Bridge mappings -> Pulumi GCP SDK -> engine
```

An import or diff defect can live at any layer. Search in this order:

1. Pulumi CLI engine releases/issues.
2. Pulumi GCP releases/issues.
3. Pulumi Terraform Bridge releases/issues.
4. Terraform Google provider releases/issues.
5. Magic Modules schema/custom code and Google API behavior.

Before upgrading Pulumi GCP, identify the embedded upstream provider release.
Do not assume the latest upstream Google fix is present in the installed Pulumi
package.

## Enforce the Import Safety Floor

Require Pulumi CLI 3.252.0 or newer for all imports. Prefer 3.254.0 or newer for
bulk/state migration work.

Pulumi issue #14836 documents a real GCP Secret Manager import where a later
update deleted all imported secrets and caused a SEV0. The engine lost import
provenance when the supplied short ID differed from the provider's canonical
ID, re-imported the object as a replacement, then deleted the same object.
`protect: true` did not block that path. The fix shipped in v3.252.0.

For every imported object:

1. Use the exact Registry import shape for the installed provider version.
2. Prefer a full project/location-qualified ID where accepted.
3. Inspect the canonical provider ID stored after import.
4. Run a second ordinary update while the old writer remains frozen.
5. Refresh and check the cloud object afterward.

Use v3.254+ import files when explicit providers, hierarchy, or supplied state
are needed. Generated declarations still require compile and semantic review.

## Cloud Asset Inventory Is a Lead, Not a Census

Cloud Asset Inventory (CAI) is eventually consistent for current data and
best-effort for history; Google states that rare updates can be missed. Most
updates appear within minutes, but content types can ingest on different
schedules and ancestor data can disagree for up to 24 hours.

Inventory consequences:

- Record `update_time` per asset/content type.
- Run at least two snapshots separated by the relevant consistency window.
- Compare `RESOURCE`, `IAM_POLICY`, and organization-policy data separately.
- Check the supported asset-type table; absence can mean unsupported, not absent.
- Relationship data requires Security Command Center Premium/Enterprise and may
  have an independent timestamp.
- CAI history covers 35 days; it is not a durable ownership history.

Cross-check CAI with service APIs, audit logs, billing, DNS, state files,
deployment pipelines, Config Connector/Kubernetes objects, and owner interviews.

## Discover Controllers Before Children

Do not import controller-created children as independent resources merely
because CAI lists them. Examples include:

- GKE-managed instance groups and service accounts
- serverless revisions
- managed service agents
- load-balancer implementation resources
- Google-managed DNS records or certificates
- service networking connections and generated routes

For each object, identify the API creator from audit logs and whether deleting
or replacing the parent recreates it. Import the highest stable ownership
boundary the provider supports.

## IAM Has Authority and Time Dimensions

GCP IAM forms are not interchangeable:

| Form | Authority |
|---|---|
| Policy | Entire policy at the scope |
| Binding | All members for one role at the scope |
| Member | One additive role/principal pair |

Never import an authoritative policy/binding from an incomplete member list.
Preserve conditions byte-for-byte until normalization is understood. Separate
inherited access from policy attached directly to the resource.

Google documents policy-change propagation as typically about two minutes and
potentially seven minutes or longer. Group membership can take several minutes
to hours, and nested groups can take longer. Therefore a dependency edge only
orders API calls; it does not prove the new permission is usable.

For a grant consumed immediately by another resource:

1. Prefer service-specific readiness checks.
2. Retry only documented transient authorization failures.
3. Do not use a fixed sleep as proof of convergence.
4. Test revocation separately; removal often propagates more slowly.

## API Enablement Creates Service Agents

Enabling an API can asynchronously create Google-managed service identities and
grant roles. Inventory service agents before IAM transfer and distinguish:

- Google-managed role grants required by the service
- organization bootstrap/landing-zone grants
- application grants
- obsolete historical grants

Do not immediately authoritatively rewrite project IAM after enabling services.
Wait for service identity creation and compare the policy again. Keep project
service resources protected during adoption. Disabling an API can disrupt data
access or dependent services even when preview shows no resource deletion.

## Remote Safety Controls Are Independent

Pulumi `protect` blocks Pulumi deletion, but it does not enable GCP deletion
protection, retention, backup, or recovery. Inventory both layers.

| GCP resource/control | Non-obvious migration fact |
|---|---|
| Cloud Storage Bucket Lock | Lock is irreversible; retention cannot be reduced/removed |
| Locked bucket project | Google applies a project lien blocking project deletion |
| Cloud KMS key ring | Key rings cannot be deleted |
| Cloud KMS key version | Destruction is scheduled, then permanent; data may be unrecoverable |
| Cloud SQL deletion protection | Does not prevent project deletion, stop, edit, or backup deletion |
| Project lien | Requires separate lien permission and may be system-created |
| Shared VPC attachment | Service project can attach to only one host; ownership crosses projects |

Do not toggle an irreversible field merely to make code match an assumption.
For locked buckets and KMS, prefer import plus explicit retention of live values;
test retirement paths without attempting destructive operations.

## Stateful Service Matrix

| Service | Adoption evidence beyond preview |
|---|---|
| Cloud SQL | Engine/region, HA, backups/PITR, network, CMEK, both protection layers, replica topology |
| GKE | Mode, release channel, master/network immutables, default node pool history, workload identity |
| Storage | Location/class, UBLA, retention lock, soft delete, lifecycle, CMEK, public access prevention |
| KMS | Purpose, location, rotation, versions, destroy schedule, dependent CMEK resources |
| DNS | Zone visibility, DNSSEC, forwarding/peering, record ownership and external controllers |
| Shared VPC | Host/service roles, subnet IAM, attachments, org constraints, cross-project service agents |
| Load balancing | Full graph, reserved addresses, certificate/DNS ownership, health and traffic checks |

Cloud SQL deserves two deletion checks: Pulumi/engine protection and the live
Cloud SQL deletion-protection setting. Google notes that instance protection
does not survive project deletion as an independent safeguard.

## Default and Permadiff Triage

Magic Modules treats changes to defaults, force-new fields, import formats,
flattening, and diff suppression as potentially breaking because they can cause
estate-wide updates or replacements. During adoption:

1. Compare the live API value, upstream Terraform schema, and Pulumi input.
2. Determine whether the server omitted, defaulted, or normalized the field.
3. Search current upstream and Pulumi issues for the exact resource/property.
4. Prefer upgrading to a fixed provider over permanent ignore rules.
5. If temporary ignore is unavoidable, name the external owner and removal gate.

Recent upstream examples include console-created PAM entitlements producing a
phantom block and forced replacement, and broad provider changes adding
deletion-policy fields that caused one-time diffs. These are reasons to pin and
canary provider versions during migration.

## Shared VPC Requires Split Ownership

Model Shared VPC by real administrative boundary:

- Host project owns networks, subnets, routes, firewall, and sharing.
- Service projects own workloads and many address objects.
- Subnet/project IAM grants `compute.networkUser` across project boundaries.
- A service project can attach to one host only.
- Existing resources do not automatically move onto the shared network; many
  must be recreated to use it.

Do not place host network and every service workload into one migration stack
for convenience. Split by privileges and lifecycle, then pass explicit outputs.

## Cutover Must Survive the Next Update

A migration is accepted only after:

1. Two-source inventory is reconciled and controller-owned children excluded.
2. Current CLI/provider floors and upstream lineage are recorded.
3. Every imported resource has a canonical ID and final parent/provider.
4. Refresh-aware preview is non-destructive.
5. IAM conditions, service agents, and propagation checks pass.
6. Stateful-service data protection and restore evidence is recorded.
7. A second ordinary update performs no unexplained operation.
8. Runtime traffic, DNS, identity, and data checks pass.
9. The old writer is disabled without destroy and monitored through one cycle.

Do not retire old state immediately. Keep it read-only for forensic mapping and
rollback until the new owner has completed an ordinary change successfully.
